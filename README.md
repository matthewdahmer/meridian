# Meridian

Chandra X-ray Observatory spacecraft thermal visualization suite. Meridian is a static multi-page website composed of three tools:

- **Pitch Sensitivity (Protractor)** — shows the maximum allowed dwell time per thermal model as a function of pitch angle, under coupled thermal constraints. Rendered as a semicircular polar plot with color-coded constraint bands.
- **Steady States** — shows Xija model steady-state temperatures as multi-line dwell curves and summary tables, one model at a time, across pitch angles and mission dates.
- **Model Dashboard** — shows historical model performance for each Chandra thermal model: telemetry vs. time, residual scatter, error histogram, pitch-bin error traces, and a configurable dwell exploration scatter plot.

All three apps share the same dark sidebar theme, Bootstrap 5, and D3 v7. All vendor assets are served locally — no CDN dependencies.

## Development Server

No build step is required for development. Serve the repository root with Python's built-in HTTP server:

```bash
cd meridian/
python -m http.server 8765
```

Then open:

| App | URL |

| Pitch Sensitivity | http://localhost:8765/protractor/ |
| Steady States | http://localhost:8765/steady_states/ |

## Generating Steady States Data

The Steady States app's page and its data both come from the `xija_steady_states` package, which lives as a sibling directory at `../xija_steady_states/`. It is not assumed to be installed — run it directly from its source tree. This requires the `ska3-dev` conda environment; data generation also needs the Chandra engineering archive.

```bash
conda activate ska3-dev
cd ../xija_steady_states/
# Install or update the page (index.html, app.js, vendor/); never add --with-tests here:
python -m xija_steady_states --setup --output-dir ../meridian/steady_states
# Generate the data:
SKA=~/AXAFDATA/SKADATA python -m xija_steady_states --output-dir ../meridian/steady_states
```

`steady_states/index.html` and `app.js` are copies of the `xija_steady_states` templates: edit them there and re-run `--setup`, not here (see `handoff.md`).

This generates `meridian/steady_states/data/` containing:
- `manifest.json` — list of all 16 thermal models
- `<nav_id>/metadata.json` — per-model config and file index
- `<nav_id>/<nav_id>_<config_id>_<date>.json.gz` — per-date chart data, gzip-compressed (25 quarterly dates per config by default, 2026:001–2032:001)
- `<nav_id>/<nav_id>_<config_id>_<date>.csv` — per-date dwell CSV
- `<nav_id>/<nav_id>_<config_id>_table.csv` — summary table across all dates

Generation covers all 16 models and all 42 configurations at 1° pitch steps (about 6 minutes for a full run on the development Mac). To restrict to specific models or dates:

```bash
SKA=~/AXAFDATA/SKADATA python -m xija_steady_states \
    --output-dir ../meridian/steady_states \
    --models aca dpa fptemp \
    --dates 2026001 2026182
```

To regenerate without skipping existing files:

```bash
SKA=~/AXAFDATA/SKADATA python -m xija_steady_states \
    --output-dir ../meridian/steady_states \
    --force
```

The protractor's `protractor/data/timbre_data_*/` directories are managed separately and are not generated by this command.

## Generating Model Dashboard Data

The Model Dashboard requires one gzip-compressed JSON file per model in `model_dash/data/`, plus a `manifest.json`. These are generated by a separate data pipeline (not part of this repository). The data files are not automatically created by any command in `meridian/` — they must be placed in `model_dash/data/` before the dashboard will show any content.

The `manifest.json` format:

```json
[
  { "nav_id": "1dpamzt", "display_name": "ACIS Electronics (DPA)" },
  { "nav_id": "4rt700t", "display_name": "OBA Forward Bulkhead" }
]
```

Each `nav_id` must match the `msid` field inside the corresponding `<nav_id>.json.gz` file exactly (case-sensitive), because `nav_id` is used for the unit lookup in `MSID_DISPLAY_UNITS`.

The full schema for `.json.gz` files is documented in `model_dash/data_file_structure.md`.

## Building for Deployment

`build.py` assembles all three apps into a single `dist/` directory ready to copy to a web server.

```bash
cd meridian/
python build.py
```

This copies `protractor/` (including `protractor/data/`), `steady_states/`, and `model_dash/` (each including its generated data) into `dist/`. Each app keeps its data in its own `data/` subdirectory. Run with `--force` to overwrite an existing `dist/`:

```bash
python build.py --force
```

To build into a different directory:

```bash
python build.py --output-dir /path/to/webroot --force
```

Verify the result by serving it locally:

```bash
python -m http.server 8765 --directory dist
```

> `build.py` warns but does not fail if `steady_states/data/` or `model_dash/data/` is absent — generate the data first before a production build.

## Regenerating Data and Deploying (`deploy.py`)

`deploy.py` runs the whole pipeline in one command. On the deployment host, run it through `deploy.csh`, which sources the Ska environment setup script (that sets `SKA`, `PATH` and the Ska Python) and then runs `python deploy.py` with the same arguments. `deploy.py` never sets `SKA` itself.

1. **steady_states data:** `python -m xija_steady_states --output-dir <meridian>/steady_states`, run from the `xija_steady_states` checkout (it isn't pip-installed). Without `--steady-states-force` it only computes missing dates.
2. **model_dash data:** `python -m chandra_model_eval --trailing-days <model_days> model_dash/data <models_root> --log-file model_dash/data/run.log` (about 1 minute per model).
3. **build:** `build.build("dist", force=True)`, then sets every directory to 755 and every file to 644, and removes `.DS_Store` files.
4. **deploy:** `rsync -a -z dist/ <dest>/` over SSH. It never deletes anything on the server.

If any step fails, the later steps don't run, so the server keeps its last good copy.

One-time setup:

```bash
cp deploy_config.example.json deploy_config.json   # gitignored; edit "dest", "xija_repo", "models_root"
./deploy.csh --dry-run                              # build, then list what rsync would change
```

`deploy.csh` always sources `/proj/sot/ska3/flight/bin/ska_envs.csh` (set in `SKA_ENVS` at the top of the script). It exits 2 if that script is missing or doesn't set `SKA`.

On a development Mac, skip the wrapper and set up the environment yourself:

```bash
conda activate ska3-dev
SKA=~/AXAFDATA/SKADATA python deploy.py --dry-run
```

| Setting | Default | Meaning |
|---|---|---|
| `dest` | (required) | rsync destination, e.g. `user@host:/path/to/webroot` |
| `xija_repo` | `~/AXAFLIB/xija_steady_states` | checkout that `python -m xija_steady_states` runs from |
| `models_root` | `~/AXAFLIB/chandra_models` | chandra_models checkout for `chandra_model_eval`; its tag is logged |
| `model_days` | `1096` | model_dash window: trailing days ending today (about 3 years) |
| `ssh_options` | `["-o", "BatchMode=yes"]` | fail instead of prompting for a password (required under cron) |

Common runs (`./deploy.csh` takes the same options):

```bash
python deploy.py                         # everything
python deploy.py --skip-model-dash       # keep the current model_dash/data/
python deploy.py --skip-data             # build + deploy only
python deploy.py --no-deploy             # regenerate + build, don't sync
python deploy.py --model-days 365        # override the model_dash window once
python deploy.py --dest user@host:/tmp/meridian_test   # override the destination once
```

Exit codes: `0` success, `1` a step failed, `2` configuration problem (all are listed before anything runs), `3` another run holds `.deploy.lock`.

From cron, call `deploy.csh` with a log file. SSH must work without a prompt (a key with no passphrase, or an agent the cron job can reach):

```cron
15 3 * * * /path/to/meridian/deploy.csh --log-file /path/to/meridian/deploy.log
```

`deploy.csh` runs with `csh -f` (no `~/.cshrc`), so cron and interactive runs get the same environment. It changes to its own directory first, so it can be called from anywhere.

> The rsync built into macOS (openrsync) rejects `--chmod=D755,F644` and silently ignores the other `--chmod` forms. That's why `deploy.py` sets permissions in `dist/` before syncing instead of passing `--chmod`.

## Testing

The Steady States JavaScript logic has a QUnit test suite in the `xija_steady_states` sibling repository. To run it:

```bash
cd ../xija_steady_states/
conda activate ska3-dev
# Install the page with the QUnit suite, and generate fixture data (no real Xija simulation required):
```

### Protractor (manual)

The protractor app has no automated test suite. Verify manually after changes:

1. Start the dev server (`python -m http.server 8765` from `meridian/`)
2. Open `http://localhost:8765/protractor/`
3. Confirm the protractor plot renders with colored bands
4. Change the Date and Chips dropdowns — plot and tables should update
5. Change a variable limit dropdown — plot re-renders without a network fetch
6. Expand the "Steady States" sidebar section — model links should appear (requires `steady_states/data/` to exist)
7. Click a model link — navigates to `steady_states/?model=<nav_id>` and pre-selects that model

### Model Dashboard (manual)

The Model Dashboard has no automated test suite. Verify manually after changes:

1. Start the dev server (`python -m http.server 8765` from `meridian/`)
2. Open `http://localhost:8765/model_dash/`
3. Confirm the sidebar populates with model names (requires `model_dash/data/manifest.json`)
4. Select a model — provenance card, quad plot, error segments card, and dwell exploration card should all render
5. Test box zoom (drag) and double-click reset in each chart
6. Test axis linking: zooming the time series X axis should update the error-time chart; zooming the scatter Y should update the time series Y
7. Click the legend in the telemetry vs. time plot — it should cycle through four corners
8. Change X/Y axis dropdowns in the Dwell Exploration card — plot and title should update
9. Toggle the "Jitter scatter" checkbox — scatter dots should jitter horizontally
10. Select a second model — all three cards should be destroyed and re-rendered cleanly
11. Verify the URL updates (`?model=<nav_id>`) on each model selection, and that loading the URL directly pre-selects the correct model

## Navigation

The sidebar is shared across all three apps:

- **Pitch Sensitivity** — links to `protractor/`
- **Steady States** — 16 model links load content in-place (SPA, no page reload)
- **Model Dashboard** — model links load content in-place; URL updates to `?model=<nav_id>` on each selection

Clicking a model in the Steady States sidebar from within the protractor navigates to `steady_states/?model=<nav_id>`, which auto-selects that model on load. The Model Dashboard sidebar is populated from `model_dash/data/manifest.json` at page load.

## Data Notes

- `protractor/data/timbre_data_*/` (protractor), `steady_states/data/` (steady states), and `model_dash/data/` (model dashboard) contain large binary/JSON files. Do not read individual scenario files into context — use the schema descriptions in `CLAUDE.md` and `model_dash/data_file_structure.md` instead. The `manifest.json` in each directory is small and may be read freely.
- The active timbre data directories are listed in `protractor/data/timbre_sources.json`. Adding a new data directory means placing it in `protractor/data/` and adding its name to that file; `build.py` copies everything under `protractor/` automatically.
- Protractor scenario files may contain literal `NaN` (not valid JSON). The app replaces `NaN` with `null` before parsing.
- Steady states chart files are gzip-compressed JSON (`.json.gz`, no `NaN` values), decompressed in the browser with `DecompressionStream`; `manifest.json`, `metadata.json` and the CSVs are plain.
- Model dashboard data files are gzip-compressed JSON (`.json.gz`). The app decompresses them in the browser using the `DecompressionStream` API. All temperature and residual values in the files are always in °C regardless of the model's display unit; the app converts to °F at render time for applicable models.
- All three apps check for the gzip magic bytes (`1f 8b`) before decompressing, so `.json.gz` files load whether the server sends them as raw bytes or with `Content-Encoding: gzip` (browser already decoded).
